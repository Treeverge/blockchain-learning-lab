# Day 1 旧源码与新版网页的规则对照

2026-10-20 核对当前仓库源码。本页是静态源码审读和可复算的哈希向量，**不表示旧 Jest / Babel / Flow 依赖或九个扩展脚本已在当前环境全部运行通过**。优先运行新版[哈希与选链实验](../03-演示文稿/chain-lab.html)和[无需安装依赖的模型测试](../tests/chain.test.cjs)。

| 位置 | 哈希与证明 | 已实现的检查 | 不应推导的结论 |
| --- | --- | --- | --- |
| 上游 `src/lib.js` | `hashBlock` 对 `index + prevHash + JSON.stringify(txs)` 求 SHA-256，**不含 nonce**；`mineBlock` 另对 `blockHash + nonce + prevHash` 求证明，直到证明首位为 `0`，但存入 `block.hash` 的是原始 `blockHash`。 | 此文件没有整条链的验证函数；原 Jest 测试主要固定快照。 | 存储的 `block.hash` 不必以 `0` 开头；快照通过也不能说明交易授权、共识或新版选链已验证。 |
| 扩展 `scripts/01-build-chain.js` | 沿用“内容哈希与证明分开”的思路，额外保存 `proofOfWork`。 | `validateChain` 检查相邻链接及内容哈希，未重新验证工作量证明。 | 输出“链有效”只在该脚本所检查的范围内成立。 |
| 扩展 `scripts/08-interactive-lab.js`、`09-lab-auto-demo.js` | 将 nonce 拼进哈希输入，直接寻找带前导零的哈希；输入编码仍是字符串拼接，与新版不同。 | `validateChain` 从第 1 块开始检查链接和内容哈希，没有检查创世锚点或前导零证明。 | 这两份脚本的“链完整”也不等于完整 PoW 验链。 |
| 新版 `assets/js/chain.js` | 对 JSON 数组 `[index, prevHash, data, nonce]` 求 SHA-256；存储哈希本身承担固定难度证明。 | `inspect` 核对哈希、链接、序号、共同创世锚点及非创世块前导零；有效候选的工作量用于教学选链。 | 它仍是文本区块模型，不校验签名、余额或真实 P2P 传播。 |

具体例子：上游创世块的 `hashBlock` 为 `978bcbca07e6258e085f4d2bfcc8a332fd01c638db96f18ba267893ff95eb91a`；原快照记录的 nonce 为 `57`。按上游公式计算，该 nonce 的**另一个证明值**为 `049e415e62dc5e6b6b07287a6a56e9296a4ab68144a0c89c45b3938a9fe0e7c8`。因此旧模型确实找到以 `0` 开头的证明，但存储的区块哈希仍以 `9` 开头。修改 nonce 不改变这份旧内容哈希；新版模型则会改变区块哈希。

九个扩展脚本属于不同阶段的教学草稿，彼此也不完全共用一套序列化与验证规则。阅读时先问“这个脚本到底哈希了哪些字段、验了哪些条件”，再与新版网页比较；不要把旧脚本的对象直接交给新版 `inspect`，也不要把任一文本模型当作真实交易有效性证明。需要授权与余额检查时，继续看 Day 3 签名 / UTXO 和 Day 2 有效链重组实验。
